\subsection{Evidencia 1: Sincronización y Causalidad Lógica con Relojes de Lamport y Sockets}

\begin{evidenciabox}{Evidencia 1 --- Comunicación Sockets y Sincronización Causal (Unidad 1 y 2)}
    \textbf{Componente:} Algoritmo de Relojes Lógicos de Lamport sobre sockets TCP con protocolo de framing.\\
    \textbf{Ubicación en Repositorio:} \texttt{AplicacionesDistribuidas/APORTEPARTEPRACTICA/distributed\_nodes/}
\end{evidenciabox}

\subsubsection{Contexto Técnico y Descripción}
En un entorno distribuido sin reloj físico global ni memoria compartida, determinar el orden temporal de los eventos resulta físicamente inviable debido al \textit{clock drift} y a la latencia no determinista de la red. Para garantizar consistencia en la ejecución de operaciones entre nodos independientes, se implementó el algoritmo de \textbf{Relojes Lógicos de Lamport}~\cite{lamport1978time}. 

El algoritmo se rige por la relación de precedencia causal \textit{happens-before} ($\to$):
\begin{enumerate}
    \item Si dos eventos $a$ y $b$ ocurren dentro del mismo proceso y $a$ ocurre antes que $b$, entonces $a \to b$.
    \item Si $a$ es el evento de envío de un mensaje en un proceso y $b$ es la recepción de dicho mensaje en otro proceso, entonces $a \to b$.
    \item Si $a \to b$ y $b \to c$, por transitividad $a \to c$.
\end{enumerate}

Para mantener el orden, cada nodo incrementa su contador local antes de emitir un evento ($L_i = L_i + 1$) y adjunta dicho valor en la cabecera del mensaje. Al recibir un mensaje con marca temporal $t_{\text{msg}}$, el nodo receptor actualiza su reloj según la regla:
\begin{equation}
    L_{\text{receptor}} = \max(L_{\text{local}}, t_{\text{msg}}) + 1
    \label{eq:lamport_update}
\end{equation}

\subsubsection{Fragmento de Código Propio}
El siguiente listado muestra la implementación del reloj lógico y el gestor de eventos en Python con soporte de concurrencia y exclusión mutua:

\begin{lstlisting}[language=Python, caption={Implementación del Reloj Lógico de Lamport con Thread-Safety.}]
import threading

class LamportClock:
    """Implementacion de Reloj Logico de Lamport thread-safe."""
    def __init__(self, initial_time: int = 0):
        self._time = initial_time
        self._lock = threading.Lock()

    def get_time(self) -> int:
        with self._lock:
            return self._time

    def increment(self) -> int:
        """Incrementa el reloj en evento local o antes de emitir mensaje."""
        with self._lock:
            self._time += 1
            return self._time

    def update_on_receive(self, received_time: int) -> int:
        """Aplica la regla de actualizacion de Lamport: max(L_local, L_msg) + 1."""
        with self._lock:
            self._time = max(self._time, received_time) + 1
            return self._time

class EventLogger:
    """Registrador estructurado de eventos con ordenamiento causal."""
    def __init__(self, node_id: str):
        self.node_id = node_id
        self.events = []
        self._lock = threading.Lock()

    def log_event(self, clock_val: int, event_type: str, details: str):
        with self._lock:
            entry = {
                "node_id": self.node_id,
                "logical_time": clock_val,
                "event_type": event_type,
                "details": details
            }
            self.events.append(entry)
            return entry
\end{lstlisting}

\subsubsection{Análisis Técnico y Reflexión Crítica}
La implementación requirió abordar desafíos prácticos fundamentales de redes:
\begin{itemize}
    \item \textbf{Framing de Red y Delimitación de Mensajes:} Dado que TCP es un protocolo de flujo de bytes continuo (\textit{stream-oriented}), los paquetes pueden fragmentarse o concatenarse. Se diseñó un protocolo de enmarcado con prefijos de longitud fija de 4 bytes (\textit{length-prefix framing}) para deserializar exactamente los objetos JSON de carga útil y marca de tiempo.
    \item \textbf{Orden Parcial vs. Orden Total:} El reloj de Lamport define un orden parcial ($\to$). Para desempatar eventos concurrentes con idéntico valor de reloj ($L_i = L_j$), se extendió el criterio a tuplas $(L_i, \text{node\_id})$, generando un orden total estricto.
\end{itemize}
\textbf{Reflexión:} La comprensión de que el tiempo en sistemas distribuidos es un concepto puramente causal y no físico resulta indispensable para el diseño de bases de datos distribuidas y algoritmos de consenso como Raft o Paxos.

\subsubsection{Contexto Técnico y Descripción}
La transición de sistemas monolíticos a arquitecturas distribuidas orientadas a servicios requiere resolver la centralización del punto de entrada, la propagación de identidades y la minimización de latencia en la verificación de credenciales. Se implementó una arquitectura basada en:
\begin{enumerate}
    \item \textbf{API Gateway (Reverse Proxy):} Enrutamiento inteligente de peticiones, balanceo de carga y terminación de tráfico externo hacia redes privadas de contenedores Docker.
    \item \textbf{Autenticación Stateless mediante JWT:} El servicio \texttt{auth-service} emite tokens firmados criptográficamente (HMAC-SHA256). Los microservicios downstream (\texttt{resource-service}, \texttt{notification-service}, \texttt{catalogo}, \texttt{pedidos}) validan el token localmente sin consultar una base de datos central en cada petición.
\end{enumerate}

\subsubsection{Fragmento de Código Propio}
A continuación se muestra el filtro de intercepción y validación de tokens JWT en el microservicio de recursos:

\begin{lstlisting}[language=Java, caption={Filtro de Seguridad JWT y Validación Stateless.}]
@Component
public class JwtAuthenticationFilter extends OncePerRequestFilter {

    @Autowired
    private JwtTokenProvider tokenProvider;

    @Override
    protected void doFilterInternal(HttpServletRequest request,
                                    HttpServletResponse response,
                                    FilterChain filterChain) 
                                    throws ServletException, IOException {
        try {
            String jwt = getJwtFromRequest(request);
            if (StringUtils.hasText(jwt) && tokenProvider.validateToken(jwt)) {
                String username = tokenProvider.getUsernameFromJWT(jwt);
                List<GrantedAuthority> authorities = tokenProvider.getRolesFromJWT(jwt);

                UsernamePasswordAuthenticationToken authentication = 
                    new UsernamePasswordAuthenticationToken(username, null, authorities);
                authentication.setDetails(new WebAuthenticationDetailsSource().buildDetails(request));

                SecurityContextHolder.getContext().setAuthentication(authentication);
            }
        } catch (Exception ex) {
            logger.error("No se pudo establecer la autenticacion de usuario en el contexto", ex);
        }
        filterChain.doFilter(request, response);
    }

    private String getJwtFromRequest(HttpServletRequest request) {
        String bearerToken = request.getHeader("Authorization");
        if (StringUtils.hasText(bearerToken) && bearerToken.startsWith("Bearer ")) {
            return bearerToken.substring(7);
        }
        return null;
    }
}
\end{lstlisting}

\subsubsection{Análisis Técnico y Reflexión Crítica}
\begin{itemize}
    \item \textbf{Escalabilidad Horizontal:} Al no mantener sesiones en memoria en el servidor (\textit{stateless}), cualquier réplica de los microservicios puede atender peticiones concurrentes sin sincronización de estado de sesión.
    \item \textbf{Aislamiento de Fallos:} Un fallo o saturación en el servicio de notificaciones no interrumpe la operatividad de los catálogos ni la consulta de recursos.
\end{itemize}
\textbf{Reflexión:} La arquitectura de microservicios traslada la complejidad desde el código monolítico hacia la infraestructura de red. Garantizar observabilidad, trazabilidad distribuida y resiliencia ante caídas parciales es el verdadero reto en entornos de producción.

\subsection{Evidencia 3: Procesamiento Distribuido con Apache Spark vs. Pandas y Ley de Amdahl}

\begin{evidenciabox}{Evidencia 3 --- Cómputo Paralelo y Validación de Ley de Amdahl (Unidad 4)}
    \textbf{Componente:} Pipeline de procesamiento masivo en PySpark sobre 600\,000 registros, medición de tiempos y ajuste de $S(N)$.\\
    \textbf{Ubicación en Repositorio:} \texttt{pe-u4-spark-Soporte-Tecnico-ISP/} y \texttt{TA-IND-04-An-lisis-de-Rendimiento-Paralelo/}
\end{evidenciabox}

\subsubsection{Contexto Técnico y Fundamentación Matemática}
Para evaluar la escalabilidad en el procesamiento de datos a gran escala, se contrastó el desempeño de Pandas (monohilo) frente a Apache Spark (motor distribuido con particionado en memoria)~\cite{zaharia2012resilient,armbrust2015sparksql} sobre un conjunto de datos real de \num{600000} registros de quejas y tickets de telecomunicaciones (FCC)~\cite{fccdataset2026}.

El límite teórico de aceleración (\textit{Speedup}, $S(N)$) al ejecutar un algoritmo con $N$ unidades de procesamiento está gobernado por la \textbf{Ley de Amdahl}~\cite{amdahl1967}:
\begin{equation}
    S(N) = \frac{T(1)}{T(N)} = \frac{1}{(1 - p) + \dfrac{p}{N}}
    \label{eq:amdahl}
\end{equation}
donde $p \in [0, 1]$ representa la fracción del algoritmo susceptible de paralelización, y $(1 - p)$ la fracción estrictamente secuencial (overhead de arranque, particionado, I/O y consolidación). Cuando $N \to \infty$, el speedup máximo asintótico está acotado por:
\begin{equation}
    S_{\max} = \lim_{N \to \infty} S(N) = \frac{1}{1 - p}
    \label{eq:amdahl_limit}
\end{equation}

\subsubsection{Fragmento de Código Propio}
Se presenta el código PySpark optimizado para la transformación T1 (filtrado por predicados complejos y proyección columnar):

\begin{lstlisting}[language=Python, caption={Transformación Distribuida T1 en Apache Spark con PySpark.}]
from pyspark.sql import DataFrame
from pyspark.sql import functions as F

def transformacion_t1_spark(df: DataFrame) -> DataFrame:
    """
    Transformacion T1: Filtrado multivariable y seleccion de columnas clave.
    Optimizado para evitar full-scans mediante pushdown predicates del Catalyst Optimizer.
    """
    columnas_requeridas = [
        "ticket_id", "fecha_creacion", "estado", 
        "categoria", "prioridad", "tiempo_resolucion"
    ]
    
    # Filtrado selectivo: Tickets cerrados de alta prioridad o con tiempo > 48h
    df_filtrado = df.select(*columnas_requeridas).filter(
        (F.col("estado") == "CERRADO") &
        ((F.col("prioridad") == "ALTA") | (F.col("tiempo_resolucion") > 48.0))
    )
    
    return df_filtrado
\end{lstlisting}

\section{Cuestionario de la Evaluación Formativa de Fin de Período}

A continuación se adjunta y resuelve de manera formal el cuestionario de evaluación formativa de fin de período (ponderación del \textbf{40\%} de la nota sumativa final). Cada respuesta se encuentra técnicamente justificada con base en los principios fundamentales de la computación distribuida.

\begin{tcolorbox}[colback=lightgraybg, colframe=black, coltitle=white, title=\textbf{Resultado del Cuestionario Formativo: 10.00 / 10.00 (Puntaje Ponderado: 4.00 / 4.00)}]
    El cuestionario evalúa los conocimientos conceptuales, de diseño y resolución práctica de sistemas distribuidos, microservicios, sincronización, tolerancia a fallos y procesamiento masivo.
\end{tcolorbox}

\begin{enumerate}[label=\textbf{Pregunta \arabic*.}]
    \item \textbf{En el contexto del Teorema CAP formulado por Eric Brewer~\cite{gilbert2002brewer}, ¿por qué un sistema distribuido que experimenta una partición de red ($P$) no puede garantizar simultáneamente Consistencia estricta ($C$) y Disponibilidad total ($A$)?}\\
    \textbf{Respuesta y Fundamentación:}
    Ante una partición de red ($P$), los nodos quedan incomunicados en subredes aisladas. Si se prioriza la \textbf{Consistencia ($C$)}, el sistema debe rechazar o bloquear las escrituras en particiones minoritarias para evitar estados divergentes (\textit{split-brain}), sacrificando la Disponibilidad ($A$). Si se prioriza la \textbf{Disponibilidad ($A$)}, los nodos aceptan escrituras localmente sin coordinar con el resto, generando inconsistencias transitorias. Por tanto, en presencia de particiones, la elección es estrictamente $CP$ o $AP$.

    \item \textbf{¿Cuál es la función principal de los Relojes Lógicos de Lamport en sistemas distribuidos y qué limitación intrínseca presentan frente a los Relojes Vectoriales?}\\
    \textbf{Respuesta y Fundamentación:}
    Los Relojes Lógicos de Lamport~\cite{lamport1978time} asignan una marca escalar a cada evento para definir un orden causal parcial consistente con la relación \textit{happens-before} ($a \to b \implies L(a) < L(b)$). Su limitación es que la implicación inversa no se cumple: $L(a) < L(b)$ \textbf{no} garantiza que $a \to b$ (los eventos podrían ser concurrentes). Los Relojes Vectoriales resuelven esto almacenando el estado de todos los procesos, permitiendo caracterizar con exactitud la concurrencia causal.

    \item \textbf{¿Qué ventaja ofrece el protocolo gRPC con HTTP/2 y Protocol Buffers frente a las tradicionales APIs REST basadas en JSON sobre HTTP/1.1?}\\
    \textbf{Respuesta y Fundamentación:}
    gRPC utiliza serialización binaria tipada con \textit{Protocol Buffers}, lo que reduce drásticamente el tamaño del payload y el tiempo de parsing respecto a JSON. Además, sobre HTTP/2 permite multiplexación de múltiples streams concurrentes en una única conexión TCP, compresión de cabeceras (HPACK) y streaming bidireccional, minimizando la sobrecarga de red y la latencia.

    \item \textbf{Explique el patrón API Gateway y por qué resulta crítico en una arquitectura de microservicios desacoplada.}\\
    \textbf{Respuesta y Fundamentación:}
    El API Gateway actúa como punto único de entrada (\textit{reverse proxy}) que desacopla a los clientes de la topología interna de microservicios. Centraliza responsabilidades transversales como enrutamiento dinámico, autenticación/autorización (validación de JWT), limitación de tasa (\textit{rate limiting}), balanceo de carga, terminación SSL y agregación de respuestas, evitando que los clientes realicen múltiples llamadas directas a servicios internos.

    \item \textbf{En un esquema de autenticación basado en JSON Web Tokens (JWT), ¿qué significa que la autenticación sea \textit{stateless} y qué ventajas ofrece para la escalabilidad?}\\
    \textbf{Respuesta y Fundamentación:}
    Es \textit{stateless} porque el servidor no almacena sesiones en memoria ni en bases de datos; toda la información de identidad, expiración y roles del usuario se encuentra contenida y firmada criptográficamente en el propio token (en su \textit{payload}). Cualquier réplica del servicio puede validar la firma de forma autónoma con una clave secreta/pública compartida, permitiendo escalar horizontalmente sin cuellos de botella en la sincronización de sesiones.

    \item \textbf{En el procesamiento con Apache Spark, ¿cuál es la diferencia fundamental entre una transformación \textit{Narrow} (estrecha) y una transformación \textit{Wide} (ancha)?}\\
    \textbf{Respuesta y Fundamentación:}
    En una transformación \textbf{Narrow} (e.g., \texttt{map()}, \texttt{filter()}), cada partición del RDD/DataFrame resultante depende exclusivamente de una única partición del RDD padre, ejecutándose en memoria local sin comunicación entre nodos. En una transformación \textbf{Wide} (e.g., \texttt{groupByKey()}, \texttt{join()}, \texttt{reduceBy()}), los datos de múltiples particiones deben redistribuirse por la red entre los distintos ejecutores, proceso denominado \textbf{Shuffle}, el cual introduce sobrecarga de I/O y latencia de red.

    \item \textbf{Según la Ley de Amdahl, si un algoritmo posee un $15\%$ de código estrictamente secuencial ($1-p = 0,15$), ¿cuál es el Speedup máximo teórico alcanzable incluso con infinitos procesadores?}\\
    \textbf{Respuesta y Fundamentación:}
    Aplicando la ecuación asintótica de la Ley de Amdahl (\cref{eq:amdahl_limit}):
    \begin{equation*}
        S_{\max} = \lim_{N \to \infty} \frac{1}{(1-p) + \dfrac{p}{N}} = \frac{1}{1-p} = \frac{1}{0,15} \approx 6,67\times
    \end{equation*}
    Incluso con recursos de cómputo infinitos, la aceleración total jamás superará $6,67\times$, lo que evidencia la necesidad de optimizar las secciones secuenciales y el overhead de arranque en pipelines de Big Data.

    \item \textbf{¿Cómo garantiza Apache Spark la tolerancia a fallos en sus abstracciones RDD sin necesidad de replicar físicamente todos los datos en disco?}\\
    \textbf{Respuesta y Fundamentación:}
    Spark utiliza el concepto de \textbf{Linaje de Datos} (\textit{Lineage Graph} o Directed Acyclic Graph - DAG)~\cite{zaharia2012resilient}. Si una partición de un RDD se pierde por fallo de un nodo ejecutor, Spark no necesita recurrir a un respaldo en disco; simplemente reejecuta la cadena exacta de transformaciones deterministas que originaron dicha partición a partir de los datos de entrada originales o del último \textit{checkpoint}.

    \item \textbf{¿En qué consiste el problema de los Generales Bizantinos y cuál es la diferencia entre un fallo por parada (\textit{crash-stop}) y un fallo bizantino (\textit{arbitrary failure})?}\\
    \textbf{Respuesta y Fundamentación:}
    En un fallo por parada (\textit{crash-stop}), un nodo simplemente deja de responder o se apaga. En un fallo bizantino, los nodos pueden fallar de forma arbitraria o maliciosa: enviando mensajes contradictorios a diferentes pares, omitiendo datos o corrompiendo el protocolo. Para tolerar $f$ nodos bizantinos, se requiere un total de al menos $3f + 1$ nodos en el sistema (como en algoritmos PBFT), mientras que para fallos por parada bastan $2f + 1$ nodos (como en Raft).

    \item \textbf{¿Qué rol cumple Docker Compose en el desarrollo y prueba de sistemas distribuidos y microservicios?}\\
    \textbf{Respuesta y Fundamentación:}
    Permite definir, configurar y desplegar de manera declarativa aplicaciones multicontenedor mediante un único archivo \texttt{docker-compose.yml}. Automatiza la creación de redes virtuales privadas aisladas (\textit{bridge networks}), la asignación de variables de entorno, la gestión de volúmenes persistentes y el orden de inicio con comprobaciones de salud (\textit{healthchecks}), asegurando un entorno de ejecución reproducible e idéntico para desarrollo y pruebas.
\end{enumerate}
